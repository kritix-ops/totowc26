# QA Agent — autonomous browser agent for sandbox QA

**Date:** 2026-06-04
**Status:** Awaiting approval

## Goals

Build an autonomous AI agent that drives the sandbox deployment
(`toto-mundial-sandbox.vercel.app`) in a real browser, exercises the
critical user flows the way a real person would, and produces a
written QA report with screenshots after each run.

The agent must behave like a careful human tester: navigate by what is
visible on the page (labels, headings, button text), notice broken
states, retry sensibly when something is slow, and write findings in
plain Hebrew/English so a person reading the report knows exactly what
to fix.

## Scope (locked from clarification round)

- **Sandbox only.** `toto-mundial-sandbox.vercel.app`. Never points
  at production. The runner refuses to start if `BASE_URL` resolves
  to the prod hostname.
- **Three scenario families:**
  1. Live bets (match picks, day bets) — golden path + deadline
     enforcement edge cases.
  2. Tournament outrights (winner, top scorer, group winners) —
     placing, editing before lock, viewing after lock.
  3. RTL + Hebrew + mobile responsive — every screen the above
     scenarios touch is also re-rendered at 360 / 414 / 768 / 1440
     and inspected for overflow, clipped text, hover-only
     interactions, and `pb-24` violations under `main`.
- **Manual trigger.** CLI command (`pnpm qa-agent <scenario>`) and
  an admin button on `/he/admin` later. No cron, no auto-on-deploy
  in this iteration.
- **Test user:** create `qa-bot@kritix.io` in the sandbox Supabase
  project with a fixed password. Approved by admin once, then reused
  every run.
- **Output:** `_qa-reports/<YYYY-MM-DD-HHmm>/report.md` with embedded
  screenshots in `_qa-reports/<...>/screenshots/`. Plus a one-line
  pass/fail summary printed to stdout.

## Constraints

- **Existing stack:** Node 20+, TypeScript via `tsx`, Playwright 1.60
  already installed, `@anthropic-ai/sdk` to be added, env loaded via
  `node --env-file=.env.local` like every other script in
  `/scripts/`.
- **Budget:** target ~$0.30 per full run (all three scenarios). A run
  that exceeds $2.00 in token spend aborts itself and writes a
  partial report so we never get a surprise bill.
- **No prod DB writes, ever.** The seed script (run once) writes
  ONLY to the sandbox Supabase project. The agent itself writes
  only via the public HTTP surface, exactly like a real user.
- **No mutation of bets that belong to other users.** Per
  `feedback_user_bets_are_sacred`, the agent operates exclusively
  under the `qa-bot@kritix.io` account. The seed script verifies the
  account's user id before every run and refuses to start if it ever
  resolves to a different uuid.

## Alternatives considered

### Option A — Custom Node agent, Playwright wrapped as Claude tools (RECOMMENDED)

A single `tsx` script under `/scripts/qa-agent/` runs the Anthropic
SDK message loop in-process and exposes Playwright as a small set of
Claude tools (`browser_navigate`, `browser_snapshot`,
`browser_click`, `browser_type`, `browser_select`, `browser_wait`,
`browser_screenshot`, `qa_record_finding`). Claude Sonnet 4.6 drives
the loop, receives accessibility snapshots after each action, and
calls `qa_record_finding` whenever it sees something wrong.

- **Why:** matches the project's existing `/scripts/*.mjs` shape,
  zero extra processes, easy to debug locally, one file to read
  end-to-end. Tool surface is intentionally a near-clone of the
  Microsoft `@playwright/mcp` tool names so we can swap to a true
  MCP transport later with one adapter file if we ever want to.
- **Tradeoff:** we own the loop ourselves, including retry on 529
  and token-budget guarding. Roughly 250 lines of glue.

### Option B — `@playwright/mcp` subprocess + custom MCP client

Spawn `npx @playwright/mcp@latest` as a child process, talk to it
over stdio using `@modelcontextprotocol/sdk`'s `Client`, forward
tool schemas to Claude.

- **Why:** "real" Playwright MCP, exactly as Microsoft ships it.
  Every improvement Microsoft makes flows in for free.
- **Tradeoff:** two extra dependencies, a subprocess to supervise,
  process-lifecycle bugs to debug. For the value we get over A
  (the tool surface is the same), it is not worth it on day one.

### Option C — Anthropic Computer Use (vision + mouse/keyboard)

True "Claude is a human" — screenshots in, click coordinates out.

- **Why:** catches purely-visual regressions A and B cannot
  (z-index, color contrast, font fallback). Most "human-like".
- **Tradeoff:** ~10x cost per run, much slower, and flaky on Hebrew
  text rendering in CI screenshots. We can add this as a fourth
  scenario later — `qa-agent --vision` — once A is paying off.

### Recommendation: **A**

Cheapest, fastest, fits the project shape. Same tool surface as
Microsoft's MCP server so a future migration is trivial. Vision
(option C) becomes a tagged sub-mode we add only if accessibility-
tree QA misses real bugs in practice.

## Architecture

```
scripts/qa-agent/
├── index.mts             # CLI entry: parse args, env guards, dispatch
├── seed-user.mts         # One-time: create qa-bot@kritix.io in sandbox
├── agent-loop.mts        # Anthropic SDK tool-use loop + budget guard
├── browser-tools.mts     # Playwright wrapped as Claude tool definitions
├── reporter.mts          # Build _qa-reports/<ts>/report.md
├── scenarios/
│   ├── live-bets.mts     # Scenario prompt + acceptance criteria
│   ├── outrights.mts
│   └── rtl-mobile.mts
└── prompts/
    └── system.md         # System prompt: persona, rules, finding format
```

**Loop shape (pseudocode):**

```ts
const sdk = new Anthropic();
const browser = await launchBrowser({ viewport: '360x800', locale: 'he-IL' });
const tools = makeBrowserTools(browser, findings);
const messages = [{ role: 'user', content: scenario.userPrompt }];

while (true) {
  const res = await sdk.messages.create({
    model: 'claude-sonnet-4-6',
    max_tokens: 4096,
    system: SYSTEM_PROMPT + '\n\n' + scenario.successCriteria,
    tools: tools.schemas,
    messages,
  });
  messages.push({ role: 'assistant', content: res.content });
  if (res.stop_reason !== 'tool_use') break;
  const results = await Promise.all(
    res.content
      .filter(b => b.type === 'tool_use')
      .map(b => tools.run(b.name, b.input).then(r => ({
        type: 'tool_result', tool_use_id: b.id, content: r,
      })))
  );
  messages.push({ role: 'user', content: results });
  if (budget.usdSpent > BUDGET_USD_HARD_CAP) break;
}
```

**Tool surface (intentionally MCP-shaped):**

| Tool                | Input                                | Returns                                 |
|---------------------|--------------------------------------|-----------------------------------------|
| `browser_navigate`  | `{ url }`                            | `{ url, title, snapshot }`              |
| `browser_snapshot`  | `{}`                                 | YAML accessibility tree (no pixels)     |
| `browser_click`     | `{ ref }`                            | post-action snapshot                    |
| `browser_type`      | `{ ref, text, submit?: bool }`       | post-action snapshot                    |
| `browser_select`    | `{ ref, values: string[] }`          | post-action snapshot                    |
| `browser_wait`      | `{ for: 'network' \| 'ms', value }`  | post-action snapshot                    |
| `browser_resize`    | `{ width, height }`                  | post-action snapshot                    |
| `browser_screenshot`| `{ name }`                           | saves to `_qa-reports/<ts>/screenshots/`|
| `qa_record_finding` | `{ severity, area, expected, actual, screenshotRef? }` | stores finding for the report |

`ref` is the numeric id from the most recent snapshot — same
convention as `@playwright/mcp`. Claude is told to call
`browser_snapshot` first and then refer to elements by `ref`, never
by guessed selectors.

## Scenarios — concrete acceptance criteria

Each scenario is one user message to Claude that pairs a goal with
checklist-style success criteria. Claude reports
`qa_record_finding` for anything that fails a criterion. The
report classifies findings: `critical` (data loss / payment / login
broken), `high` (flow blocks the user), `medium` (UX papercut),
`low` (cosmetic).

### Live bets (`pnpm qa-agent live`)
- Log in as `qa-bot@kritix.io`.
- Navigate to `/he/bets`. Confirm match list renders in Hebrew with
  team names and kickoff times in Asia/Jerusalem.
- Open a match whose kickoff is >60 min away. Place a 1X2 pick.
  Reload the page. Pick still selected.
- Open a match whose kickoff is <5 min away. Form is disabled with
  a clear Hebrew lock message. (Per
  `project_betting_deadlines.md`.)
- Place a day-bet on today's matchday. Confirm balance/notation
  matches `project_points_model.md` (total == available).

### Outrights (`pnpm qa-agent outrights`)
- Navigate to `/he/tournament-bets`. Confirm all five categories
  (winner, runner-up, top scorer, group winners, top scorer per
  team) render.
- Place one pick in each category. Confirm picks persist after
  reload. Confirm stake shown is 0 per
  `project_free_tournament_bets.md`, and max payout shown is 25.
- Try to edit a pick whose deadline has passed (if any are locked).
  Confirm the UI shows a lock and the API refuses.

### RTL + Hebrew + mobile (`pnpm qa-agent rtl-mobile`)
- For each page touched by the two scenarios above, plus `/he`,
  `/he/leaderboard`, `/he/bracket`, `/he/profile`, `/he/admin`:
  - Render at 360, 414, 768, 1024, 1440 (per `CLAUDE.md` rule).
  - Run an in-page check for `scrollWidth > innerWidth + 1` and
    record offending elements (steal the snippet from
    `scripts/mobile-screenshots.mjs`).
  - Record any element with `unicode-bidi` direction inconsistency
    (Latin name inside a Hebrew sentence rendering LTR-inside-RTL
    wrong).
  - Verify `main` has `pb-24` (or equivalent computed
    `padding-bottom`) on viewports < `md`.
  - Tap-target audit: every `button`, `a`, `[role=button]` must
    have bounding-box >= 44x44px on the 360 viewport.

## Security (rule 13)

- **Env separation.** Seed-user script reads
  `SANDBOX_SUPABASE_URL`, `SANDBOX_SUPABASE_SERVICE_ROLE_KEY`,
  `SANDBOX_DIRECT_URL`. It refuses to run if any of those resolve
  to the prod project (check substring match against
  `PROD_DATABASE_URL` if present; otherwise compare to a hard-coded
  prod hostname list).
- **Runner refuses prod target.** Agent aborts at startup if
  `BASE_URL` matches a prod hostname (`toto-mundial.vercel.app`,
  `toto-mundial.kritix.io`, or anything without `sandbox` in the
  host).
- **No secrets in screenshots.** `qa-bot@kritix.io`'s password lives
  only in `.env.local`, never in the report. Cookies are cleared
  between scenarios.
- **No bet mutation outside the bot account.** Loop guards every
  `browser_navigate` URL against `/admin/*` paths that would let
  the agent see other users' data. `qa-bot` is provisioned as a
  regular `member`, not `admin`. (A separate `--admin-flow` mode
  with explicit `--i-know-this-touches-admin` would unlock those
  paths, but it is out of scope here.)
- **API key hygiene.** `ANTHROPIC_API_KEY` is read from
  `.env.local` (already present). The agent never logs the key,
  never embeds it in a screenshot, never sends it back to Claude
  in a tool result.

## Observability (rule 14)

- Every step the agent takes emits a namespaced log line to the
  terminal AND to `_qa-reports/<ts>/trace.log`:
  - `[qa.boot]` env checks, browser launch
  - `[qa.scenario]` scenario start/end with elapsed
  - `[qa.tool]` every tool call: name, input, ms, result-summary
  - `[qa.budget]` after every model call: tokens in/out, $ this
    call, $ run-total
  - `[qa.finding]` every `qa_record_finding` with full payload
  - `[qa.fatal]` any unrecoverable error, including budget cap hit
- Values, not labels. `[qa.tool] browser_click ref=14 ok 312ms`
  beats `clicking element`.
- The Anthropic SDK request-id is logged on every call so a failed
  run can be traced server-side if needed.

## Testing (rule 18)

The agent itself ships with unit tests under
`scripts/qa-agent/__tests__/`:
- `budget.test.ts` — budget guard trips at the configured cap,
  emits the right log line, returns a partial report.
- `tools.test.ts` — each browser tool against a fixture HTML page
  served by Playwright's built-in static server. Verifies snapshot
  output, ref-based clicking, screenshot path naming.
- `reporter.test.ts` — given a known set of findings, produces a
  byte-stable `report.md` with embedded screenshot links and a
  correct pass/fail summary line.
- `seed-user.test.ts` — mocks Supabase admin client, verifies the
  prod-DB-refusal logic with three positive and three negative
  fixtures.

End-to-end: a `qa-agent:smoke` script runs the agent against a
local Next.js dev server with a tiny scripted scenario (open a
single page, snapshot, assert one finding) so CI can catch
agent-loop regressions without spending real Claude budget. Uses
`@anthropic-ai/sdk` request mocking via `nock`.

Vitest is already the project's test runner; new tests slot into
`vitest.config.ts` with no changes.

## Open questions for the user

1. **Sandbox creds.** I do not have `SANDBOX_SUPABASE_URL`,
   `SANDBOX_SUPABASE_SERVICE_ROLE_KEY`, `SANDBOX_DIRECT_URL` in
   `.env.local` today. Should I (a) add them to your local file
   so the seed script works, or (b) build the seed script anyway
   and have you fill them in before the first run?
2. **First-run admin approval.** After the seed script creates
   `qa-bot@kritix.io`, it lands as a pending signup_request. Do
   you want the seed script to bypass approval (write
   `is_approved=true` and `is_paid=true` directly), or should the
   first run be a manual approval through `/he/admin` like a
   normal user?
3. **Report retention.** Keep all `_qa-reports/*` forever, or
   prune to the last N runs? Defaulting to "keep last 20" unless
   you prefer otherwise.
4. **Add `.env.sandbox` to `.gitignore`.** If we go with a
   separate env file for sandbox creds (cleaner than mixing into
   `.env.local`), I will add it to `.gitignore` — confirming you
   are OK with that file pattern.
